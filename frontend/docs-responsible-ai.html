OoruShare · Responsible AI Documentation

Responsible AI Principles

RAI-001 · v1.0 · Nov 2026

Executive Summary

OoruShare is a hyperlocal loading-dock coordination platform operating across Bengaluru's residential neighbourhoods. It uses algorithmic scheduling (staggered dispatch), geospatial data, and community credit scoring to coordinate three user groups: residents, delivery riders, and dark store operators. This document establishes the Responsible AI (RAI) principles governing all algorithmic and data-driven decisions within the system.

01

Fairness

Equal access to spots regardless of platform affiliation or rider identity

02

Transparency

All scheduling logic is deterministic and explainable to every stakeholder

03

Accountability

Human override at every automated decision point; full audit trail

04

Privacy

Minimum data collection; no PII beyond display name; location data bounded

05

Safety

Rate limits, advisory locks, and graceful degradation prevent system abuse

06

Inclusivity

No algorithmic barriers based on caste, religion, language, or platform

1 · Fairness

1.1 Spot allocation

Spots are allocated on a strict first-come, first-served basis enforced by a PostgreSQL advisory lock (pg_try_advisory_xact_lock). No rider receives preferential access based on platform, rating, or past booking history.

Implementation: The advisory lock key is 42000000 + spot_id. Only one booking transaction per spot can hold the lock at any moment — no side-channel for platform-level priority.

1.2 Dispatch staggering

The staggering algorithm — scheduled_at = MAX(pending for store) + stagger_mins — treats all riders from the same store equally. The default 4-minute gap is configurable per store but applies uniformly to every rider in the queue.

1.3 Credit scoring

Community credits are awarded at a flat rate of 10 credits per booking regardless of platform, duration extension, or rider identity. No gamification that could skew resident participation toward high-volume platforms.

1.4 RWA approval

RWA admins can approve or reject spots. To prevent discriminatory rejection patterns, the RWA admin dashboard surfaces the neighbourhood and address only — no rider or platform data is shown at the approval stage.

Risk: Rejection decisions by RWA admins carry human bias risk. Mitigation roadmap: Log all approve/reject actions with timestamps; flag spots rejected more than twice without resolution for escalation review.

2 · Transparency

2.1 Algorithmic explainability

Decision Algorithm Explainability to user
Which spots appear on the rider map All approved spots with status=available, ordered by map proximity Legend shows colour-coding; tooltip shows address and gate width
When a rider is scheduled to dispatch MAX(pending scheduled_at for store) + stagger_mins Countdown timer shows exact time; store operator sees full queue
How many credits a resident earns Flat 10 per completed booking Credit history table shows reason and booking_id for every entry
Why a spot is unavailable status field: available / booked / unavailable Marker colour + panel text explains current state

2.2 No hidden scoring

OoruShare does not maintain hidden reputation scores for riders, residents, or dark stores. The only derived value is total_credits for residents, which is a transparent sum of logged credit events.

2.3 Open-source logic

All scheduling, credit, and approval logic is in plain Node.js — no ML models, no black-box vendors. Any operator can audit the exact SQL queries executed for every decision.

3 · Accountability

3.1 Human override points

Automated action Human override available
Spot auto-released after 2 minutes Resident can mark spot unavailable at any time; rider can cancel booking early (DELETE /bookings/:id)
Dispatch scheduled by stagger algorithm Dark store operator can manually dispatch any rider immediately via the Dispatch button
RWA status defaults to "approved" RWA admin can reject at any point; reversal is also available
Credit awarded automatically on booking Platform admin can void credits (future roadmap — not yet implemented)

3.2 Audit trail

Every state change is persisted with a created_at or booked_at timestamp. The credits table links each award to a booking_id for complete end-to-end traceability. The X-Request-Id correlation header ties API calls to structured server logs.

3.3 Incident response

The graceful shutdown handler drains SSE clients and in-flight requests before stopping, preventing corrupted booking states during deployments. PostgreSQL transactions with ROLLBACK ensure no partial bookings persist.

4.2 Location data

Sensitive data notice: Residential addresses and GPS coordinates are stored in plain text. Production deployments must enable PostgreSQL column-level encryption or use a cloud KMS-backed storage solution before handling real residential data at scale.

4.3 B2B Fleet Integration & DPDP Act 2023 Compliance

In accordance with India's Digital Personal Data Protection (DPDP) Act 2023, delivery platforms (Blinkit, Zepto, Swiggy) enter into a Business Associate Agreement (BAA) / Civic Integration SLA with OoruShare. Active delivery shifts and drop targets are ingested via automated webhooks (POST /integrations/dispatch). Rider identities are strictly pseudonymized via tokenized identifiers (e.g. rider_token: "BLK_HSR_4021"). Riders do not undergo separate KYC or redundant onboarding, eliminating friction while ensuring zero PII leakage to driveway owners.

5 · Safety & Robustness

5.1 Abuse prevention

  • Rate limiting: 300 API requests/minute per IP; 10 booking attempts/minute per IP+spot
  • Body size cap: 64 KB maximum request body
  • Input validation: Required fields enforced at API layer; status values allowlisted
  • SQL injection: All queries use parameterised statements — no string interpolation

5.2 System degradation

  • Without Redis: falls back to in-process EventEmitter — SSE continues for single-instance deployments
  • Without PostgreSQL: falls back to in-memory store — system remains functional for demos/dev
  • SSE client disconnects: heartbeat every 25 s detects dead connections; graceful shutdown closes all SSE streams before process exit

5.3 Out-of-scope risks and mitigations

6 · Inclusivity & Equity

OoruShare operates in mixed-income residential neighbourhoods. The platform is designed to serve gig workers — a population that is often underserved by formal infrastructure — by giving them access to legal, predictable loading space. The following design choices reflect this commitment:

  • No app install required: Progressive web interface works in any browser, including low-end Android devices
  • No language barrier: Interface targets English-literate users; Kannada/Hindi localisation is on the roadmap
  • No platform lock-in: All four major Bengaluru delivery platforms (Blinkit, Zepto, Swiggy, Dunzo) are supported equally
  • Community benefit: Credits earned by residents are redeemable for neighbourhood maintenance — value flows back to the community, not a central profit centre
