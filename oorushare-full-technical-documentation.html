1 · Product Overview

OoruShare turns unused residential driveway space into shared, bookable loading bays for last-mile delivery riders operating in Bengaluru's narrow bylanes. It coordinates three actors who were never connected before:

RoleProblem they haveWhat OoruShare gives them
ResidentDriveway blocks bikes, no benefit from sharingSelf-service listing form, 10 community credits per booking, live status toggle
RiderNo legal loading spots, forced to double-park, get finedLive map of available spots, 2-minute slot booking with sub-3s confirmation
Dark StoreMultiple riders reach the same street simultaneously → gridlockStaggered dispatch queue (4-minute gaps), surge simulation, live congestion bars

The system is designed as a zero-framework, zero-build-step application: plain HTML + CSS on the frontend, Node.js + Express on the backend, PostgreSQL for durability, and Redis for real-time fan-out at scale.

3 · System Architecture

SSE fan-out explained

Before scaling, every connected SSE client had its own setInterval firing 2 DB queries every 3 seconds — O(N) DB load. After the Redis refactor:

  • One DB poller per Node process publishes a snapshot to the oorushare:live Redis channel.
  • All local SSE clients receive the message via a single shared subscriber connection.
  • DB load is constant at 2 queries / 3 s regardless of how many clients or replicas are running.
Booking concurrency: POST /bookings acquires a PostgreSQL advisory lock (pg_try_advisory_xact_lock(42000000 + spot_id)) inside a transaction before checking availability. Concurrent booking attempts on the same spot get a deterministic 409 rather than a race condition.

7 · API — Bookings /bookings

GET /bookings

Query Parameters

ParamTypeDescription
spot_idnumberFilter to bookings for a specific spot

Returns up to 100 bookings ordered newest-first. Fields: id, spot_id, rider_name, platform, booked_at, duration_mins, status.

POST /bookings

Rider books a 2-minute loading slot. This endpoint uses a PostgreSQL advisory lock to prevent concurrent double-booking on the same spot.

Rate limited: 10 requests per minute per IP+spot_id combination. Returns 429 when exceeded.

Booking flow

  1. Acquire advisory lock pg_try_advisory_xact_lock(42000000 + spot_id)
  2. Verify spot status is available
  3. Insert booking record
  4. Set spot status → booked
  5. Insert 10 credits for the spot owner
  6. COMMIT transaction (advisory lock released)
  7. Schedule setTimeout to auto-release after duration_mins
  8. Publish updated snapshot to Redis SSE channel

Request Body

FieldTypeRequiredDefaultDescription
spot_idnumberYes—ID of the spot to book
rider_namestringYes—Rider's display name
rider_phonestringnullContact number
platformstring"Blinkit"Blinkit | Zepto | Swiggy | Dunzo
duration_minsnumber2Slot duration in minutes

Responses

StatusBody
201Created Booking object
400{ "error": "spot_id and rider_name are required" }
409{ "error": "Spot is not available" } or "Spot is being booked by another rider"
429{ "error": "Too many booking attempts — please wait a moment." }

DELETE /bookings/:id

Cancel a booking early. Immediately restores the spot to available and publishes to SSE.

StatusBody
200Cancelled Booking with status: "cancelled"
404{ "error": "Booking not found" }

11 · API — SSE Live Stream /live

Server-Sent Events endpoint. Push interval configurable via SSE_INTERVAL_MS (default 3 000 ms).

const sse = new EventSource('http://localhost:3001/live');
sse.onmessage = e => {
  const { spots, queue } = JSON.parse(e.data);
  // spots: Spot[] — all spots with live status
  // queue: DispatchQueueEntry[] — up to 20 pending dispatch entries
};
Header set by serverValue
Content-Typetext/event-stream
Cache-Controlno-cache
X-Accel-Bufferingno (disables nginx buffering)

A : heartbeat comment is sent every 25 seconds to keep the TCP connection alive through proxies. The client automatically reconnects (browser EventSource behaviour).

Fan-out architecture: Adding more Node replicas does not increase DB load for SSE. All replicas share one Redis pub/sub subscription — the DB is queried once per interval per process, not once per connected client.

15 · Scaling Guide

Bottlenecks addressed

BottleneckBeforeAfter
SSE DB loadO(clients × 2 queries / 3 s)O(2 queries / 3 s) — Redis pub/sub fan-out
Booking racesCheck-then-set (racy under concurrency)PostgreSQL advisory lock in transaction
DB connections10 (pg default), no tuningConfigurable POOL_MAX + PgBouncer in front
Runaway queriesNone — queries could run foreverstatement_timeout set per connection
Abuse / botsNo protectionRate limiting (300 req/min API, 10 req/min bookings)
Response sizeUncompressed JSONgzip / brotli via compression middleware
Observabilityconsole.log unstructuredStructured JSON logs + X-Request-Id correlation
Process crashIn-flight requests and SSE state lostGraceful shutdown: drains SSE, waits up to 30 s
Single CPUSingle-threaded Node processNODE_CLUSTER=1 forks one worker per CPU core
Single instanceOne backend containerdocker compose up --scale backend=N + Redis fan-out

Horizontal scaling (multiple containers)

# 4 API replicas sharing Redis + PgBouncer
docker compose up --scale backend=4

# Tune per environment
POOL_MAX=5            # low per-process when PgBouncer in transaction mode
SSE_INTERVAL_MS=5000  # relax push frequency under heavy read load
RATE_API_MAX=500      # raise for trusted internal services

Vertical scaling (single large machine)

NODE_CLUSTER=1 node server.js   # forks one worker per CPU core

TierSetupEst. concurrent SSE clientsEst. API req/s

Production checklist

  • Set DATABASE_URL with sslmode=require for cloud-hosted PostgreSQL.
  • Set REDIS_URL to point at a managed Redis or Redis Cluster.
  • Place an nginx / traefik / ALB load balancer in front of backend replicas on port 3001.
  • Set POOL_MAX=5 per backend container when PgBouncer is in use.
  • Configure app.set('trust proxy', 1) is already enabled — ensure your LB sends X-Forwarded-For.
  • Set NODE_ENV=production to enable Express production optimisations.
  • Use SIGTERM for rolling restarts — the graceful shutdown handler drains SSE clients and waits up to 30 s before exiting.
  • Monitor X-Request-Id in your log aggregator (Datadog, CloudWatch, etc.) for distributed tracing.
